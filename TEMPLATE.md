# Inspection-company dashboard template — implementation and onboarding guide

This repository is an operational dashboard for an inspection company running WhatsApp inspection-due and overdue outreach. It ships a React/Vite frontend, an Express API on Vercel, a Supabase data backend, and external sender/booking integrations. **A `template` Git branch is a reusable starting point, not a live customer tenancy.** Each new inspection company needs its own deployment, database/data boundary, configured workers, credentials, and acceptance tests. Do not put several companies into one Vercel project pointed at one unscoped service-role database: this application is not tenant-aware.

## What this version already offers

- Login-gated pages: Today, Conversations, Performance, Controls, and Booking Capture. Desktop and mobile navigation share the same API.
- Company branding via `client/public/company-logo.png` (sidebar and login), `client/public/company-mark.png` (favicon), `client/index.html` (title), and PDF metadata in `client/src/lib/exportPerformanceReport.js`. Replace *all* brand surfaces when cloning.
- Configurable station registry in `tj_station_pause`. Controls can add a station with an integer ID and display name; new records begin paused. Controls and Capture use the same registry; Performance reads the same table to label stations. Assign an ID in every upstream system before resuming the station. Do not assume adding a row registers the station with the external sender.
- Today and Performance use **the same all-time tracked booking count and rate**. Formula: `100 × tracked bookings ÷ distinct delivered contacts`. A delivered contact has at least one `delivered` or `read` message receipt; `sent`, `failed`, and `accepted` do not count. Multiple messages and reminders to the same phone count as **one contact**. An unavailable/zero denominator displays `—`. Week/Month Performance shows a booking-detection-date headline, while its rate uses bookings attributed to outreach sent in the selected period over distinct contacts with a delivered message sent in that period; those two booking counts need not match. By-station rows display tracked bookings, distinct delivered contacts, and their ratio using the outreach station (not the calendar location). This is observational tracking, not proof the message caused a booking.
- Controls show global due-soon/passed switches, station pause flags, and a manual-batch request. The dashboard awaits an HTTP acknowledgement from n8n; session-progress polling records sessions, **not confirmed message delivery**. Inspect provider receipts before claiming delivery.
- Booking Capture sends a compressed screenshot to an n8n vision worker, presents registrations for review, and upserts approved booking observations into Supabase. Changing station/week clears reviewed rows to prevent misfiled captures.
- A PDF export of tracked bookings, delivered-based rate, funnel, stations, observed send windows, and capture freshness; no causal-impact estimation model is included. The sender schedule remains external to this repository: observed send hours are derived from outbound sessions, and the dashboard neither reads nor writes the n8n schedule.

## Architecture and trust boundaries

| Boundary | Current responsibility | New-company mapping |
|---|---|---|
| Browser | React pages, client-side queries, no secrets | Logos, names, locale, mobile layout, copy, and optional features |
| Vercel API | Express `/api/*`, signed dashboard session, service-role database access | Own project, strong auth secret, restrict who can administer outreach |
| Supabase | Outreach sessions, message rows, leads, booking snapshots, station pause/config, chat | Separate project or strict isolated schema plus access review; service-role key stays server-only |
| n8n feeder | Select/schedule leads and actually send through a messaging provider | Company-specific workflow, dedupe, opt-outs, pause enforcement, rate limits, delivery recording |
| Vision worker | OCR/normalize calendar screenshots | Change extraction format or replace with a direct booking feed |
| Doris bridge | Remaining due-soon lead-pool estimate | Map a new source to the expected response, or hide the pool if unavailable |
| YCloud | WhatsApp provider message status polling | Map new provider IDs and final states; supply a rotated server-only key |

No source-controlled n8n workflow definition, base-table creation migration, generic booking ingestion adapter, or complete schema exists here. The old TJ-specific experimental view setup was removed along with the discontinued estimation feature; it was never a full install script. Provision the *base schema* and worker workflows separately for each client before deploying. Never assume swapping the logo and `SUPABASE_URL` alone makes a working new company.

## Recommended per-company delivery model

1. Create a new private code repository or deployment branch from `template`. Keep `template` clean and free of client credentials, screenshots, and live CSVs. Preserve one Vercel project and one Supabase project per company initially; this limits blast radius and avoids implementing multi-tenant RLS in a service-role app. Point the company's custom domain at its Vercel project. Production deploys should come from its dedicated branch/CI flow, not whichever feature branch was deployed last by CLI.
2. Name the company and choose an owner/operator. Record legal/display name, sidebar and login wordmark, favicon mark, timezone, locale, currency, phone normalization and plate format; document how booking data is sourced (direct booking feed vs captured snapshots) and who owns ongoing capture.
3. Inventory the company's source systems. Identify where *leads*, *outreach sessions*, *provider message receipts*, *chat messages*, *inspection bookings*, and *station metadata* originate. Define stable IDs and timestamp timezone. If a source is missing, suppress the dependent metric instead of pretending it is zero. Require a working read-only fixture for each connector before using real customers.
4. Create and secure a company database and Storage bucket. Define the existing API-facing table contract or write an adapter. Inspect grants and RLS for **every public table**. TJ's connected database had publicly granted tables without RLS; do not clone those permissions. Decide whether browsers ever need direct Data API access; in this architecture they should use only the authenticated Express API. Keep service-role credentials in Vercel, never in `VITE_*`, browser code, screenshots, or tracked `.env` files. Stage and verify any RLS/grant changes because other consumers may depend on the database.
5. Configure sender/vision/bridge/provider secrets separately for production and preview. Require an authenticated webhook or scoped internal network protection for n8n; a URL alone is not an authorization mechanism. Start global sending **off** and all new stations paused. Do not point a preview project at the production sender unless testing a deliberate dry-run mode.
6. Run ingestion against a small synthetic or consented dataset, then check station coverage, booking matching, delivery counters, PDF output, login protection and scheduling safety. Compare dashboard counts to independent source-of-truth queries. Have a human owner sign off before enabling any station or automation.

## Data contract to adapt for a new company

These are the current application-facing entities; create a mapping layer at the ingestion boundary instead of teaching every page provider-specific fields:

- `tj_outbound_sessions`: one row per outreach session, stable `id`, `number`, `customer_id`, `station_id`, `campaign_type` (`due_soon`/`passed`), `last_outbound_at`, `last_inbound_at`, `stop_reminders`, `stop_reason`, `next_reminder_at`, `reminder_stage`, and `raw_data`. The code currently looks for `raw_data.tj_outbound.vehicles[].registration`, `customer_name` or `contact_person`. Replace the `tj_outbound` raw-data coupling with a normalized ingestion adapter before using a non-TJ sender.
- `tj_message_status`: one row per actual provider message, stable `id`, `number`, `status`, `sent_at`, optional `stage`, `wamid`, `ycloud_id`, `delivered_at`, `read_at`. Normalize provider updates to `accepted`, `sent`, `delivered`, `read`, `failed` (or a documented extension). A `read` receipt must remain eligible for the delivered denominator. Never count phone numbers as message rows.
- `tj_booking_snapshots`: stable `id`, `reg`, `station_id`, `station_name`, `week`, `appointment_week_start`, optional `appointment_date`, `first_seen_at` and `is_baseline`. `first_seen_at` is observation time, **not guaranteed booking-created time**. Only claim stronger attribution if the new source supplies booking chronology. The snapshot upsert requires a unique `(station_id,reg,appointment_week_start)` constraint.
- `tj_station_pause`: stable positive integer `station_id`, `station_name`, `paused`, `pause_outbound`, `pause_reminders`, `reason`, `updated_at`. Start additions paused; treat this as a dashboard registry, not proof the external worker honors it. Existing TJ station IDs are 58, 59, 60, 61 and should not be reused as another company's identifiers by accident.
- `tj_config`: row `id='main'` with `auto_send_due_soon`, `auto_send_passed`, `updated_at`. Seed both toggles to false. This is global scheduling state, not a per-station campaign matrix; the displayed station toggles reuse these global flags.
- `tj_csv_leads`: imported potential customers/inspection dates, used by the sender and/or historic data flows. Decide whether another client needs this exact table; don't retain an unused table with public read grants.
- `chat_history`: current chat lookup uses a TJ-prefixed normalized-phone session ID. Adapt chat identity before cloning; a successful Conversations list does not prove chat history works.
- Storage bucket `booking-captures`: private screenshot archive used by capture extraction. Establish retention, access control, consent, deletion, and image size policy per company.

All API queries use `api/lib/supabase.js` with the server-only service-role key. `fetchAll` pages PostgREST results in stable ID order; when mapping a new provider, maintain correct pagination and deduplication. `api/routes/customers.js` now pages sessions too. Several joins still use phone/plate heuristics, so reused numbers/plates, historic appointments, and missing delivery receipts can skew apparent rates. These must be audited before promising commercial attribution.

## Connector acceptance contracts

**Feeder — `POST N8N_FEEDER_WEBHOOK`:** dashboard sends `{ "max_leads_to_send": 50, "lead_type": "due_soon" }` and awaits HTTP success (timeout 55 seconds). The worker must verify the requested size, filter prior contacts and opt-outs, check `tj_station_pause` for each station, honor `tj_config` global controls where appropriate, enforce any experimental holdouts independently, and record outbound session plus provider message ID. Externally scheduling more than 55 seconds should return an explicit accepted-job response and expose a job-status API; do not interpret unchanged session counts as proof all messages were delivered. Configure the n8n webhook/auth and test a dry-run before enabling real sends. This repository does not contain n8n code, so worker-side enforcement is a **required external verification**.

**Lead-pool bridge — `POST DORIS_BRIDGE_URL/api/doris/lead-pool/summary`:** sends `{ "lead_type": "due_soon", "refresh": false, "excluded_numbers": [], "excluded_customer_ids": [] }` with `X-API-Key` if configured. Return `total_remaining` and per-station counts (the client currently tolerates `station_counts`, `by_station`, or `stations`). Map station IDs to registry IDs. The API requires an explicit `DORIS_BRIDGE_URL`; supply and test a client-owned bridge URL. If no bridge exists, hide the lead-pool tile until a connector exists.

**Vision worker — `POST N8N_BOOKING_VISION_WEBHOOK`:** request includes `{ "station": "Central", "station_id": 101, "week_start": "2026-09-28", "image_base64": "data:image/jpeg;base64,..." }`. Expect `{ "ok": true, "bookings": [{ "registration": "ABC-123", "customer_name": "Sample", "day": "Monday", "time": "10:30" }] }`. The UI permits review before commit; the server enforces Finnish registration pattern `/^[A-ZÄÖ]{2,3}-\d{1,3}$/`. Implement each country's plate validation before onboarding outside Finland. A direct booking feed can bypass image capture but must write observations with honest provenance and chronology.

**Messaging provider:** `api/routes/messages.js` currently polls YCloud `GET /v2/whatsapp/messages/{ycloud_id}` and maps `deliverTime`/`readTime`. Store credentials in `YCLOUD_API_KEY`; there is no checked-in fallback key. For another provider, implement its receipt/webhook adapter and preserve stable message-row IDs, send timestamps, delivered/read transitions, and failure reasons. Test 50-message pagination and at least one reminder per contact.

## Branding checklist

Replace both `client/public/company-logo.png` and `client/public/company-mark.png` with approved company assets. The first is a wide wordmark in the sidebar and login; the second is a square mark for browser tabs. Update `client/index.html` title, login language strings in `client/src/pages/Login.jsx`, PDF header/footer/filename in `client/src/lib/exportPerformanceReport.js`, and any hard-coded product references elsewhere. Company colors are in `client/src/index.css` (`--logo`, `--logo-2`, base and dark theme tokens). Keep contrast acceptable in both themes. Review the greeting (currently generic), schedule claims in Today/Controls, campaign labels, currency and message price, email/phone formatting, date/time and week logic (`api/lib/helsinki.js`, `client/src/lib/helsinki.js`, `client/src/lib/format.js`), raw `tj_outbound` and `tj-` chat ID prefixes. `client/public/avatar-pyry.png` is a legacy asset; remove or replace if it becomes used. PDF export is a separate branding surface, not just a screenshot of the dashboard.

## Secrets and environments

Copy `.env.example` to an ignored local env file for development, then configure Vercel project variables separately (never commit actual values). The minimum production set is `SUPABASE_URL`, `SUPABASE_SERVICE_ROLE_KEY`, `DASHBOARD_USER`, `DASHBOARD_PASSWORD`, `AUTH_SECRET`, `N8N_FEEDER_WEBHOOK`; enable `N8N_BOOKING_VISION_WEBHOOK` for Capture, `DORIS_BRIDGE_URL` and `DORIS_BRIDGE_API_KEY` for lead pool, and `YCLOUD_API_KEY` for YCloud polling. `AUTH_SECRET` must be a long random value and is required in production. `STATION_SEED_JSON` is optional for a completely empty registry and seeds stations paused; existing registry rows remain authoritative. TJ production received an explicit bridge URL and original station seed during this rollout. `CAMPAIGN_RESTART_AT` is optional when reporting a migrated campaign separately from its older send history; omit it to use all history. Do not use first-boot seed values as an ongoing source of truth. Vercel project settings, domain aliases, and sender credentials are not copied by a Git branch.

## Station onboarding runbook

1. Reserve a permanent integer station ID in the company's booking/calendar system and outbound sender. Do not reassign existing IDs. Check schedule, consent scope, location name and reporting timezone.
2. Add the station in Controls or seed `tj_station_pause` as paused. Verify `GET /api/feeder/station-pause` returns exactly the same name and ID; Capture and Performance must show the same station after queries refresh.
3. Update the external lead feed, n8n sender, calendar/vision mapping, and any bridge station mapping. Run a **dry-run** that selects eligible and excluded leads; verify pauses prevent first contacts and reminders and that duplicate sends/opt-outs are excluded. This is outside the dashboard code.
4. Confirm delivery rows and a test booking map back to the correct station; inspect the booking-rate denominator for that station. Only after sign-off resume the station. A newly added station does not automatically make an external scheduler aware of it.
5. Monitor first live batch receipts and captured bookings. If any connector fails, pause the station rather than treating missing counts as zero.

## Safety, limitations, and verification before launch

- Global campaign toggles must be off and new stations paused until sender verification. There is no implemented in-app per-company tenant boundary or audited RBAC. The signed dashboard cookie is one shared admin account, not a full user/role system. Review cross-origin settings, CSRF, rate limiting, audit logging, and access revocation before giving this to many operators.
- Supabase's `service_role` bypasses RLS for trusted API operations. Browser clients must never receive that key; protect public-schema tables from `anon`/`authenticated` separately. Before changing RLS/grants on an existing shared database, inventory other applications. Current TJ production RLS exposure was found in the connected project and is **not fixed by this template branch**.
- Rotate the YCloud key formerly committed in repository history. Removing its literal from HEAD does not remove it from Git history or revoke it; verify replacement provider credentials and test status polling.
- Attribution is matched by normalized registration, not definitive proof a WhatsApp message created a booking. Snapshot `first_seen_at` is not a booking-created timestamp. Multiple sessions/plates or messages without matching phones can affect rates; do not cap rates at 100% to hide data problems. Compare against direct source totals before reporting externally.
- There is no comprehensive e2e suite; run `npm ci`, `npm ci --prefix client`, `npm test`, `npm run build` and check `/api/health`, unauthenticated `/api/customers` (must be 401), authenticated all-time/week/month analytics, Today/Performance booking counts, `/api/feeder/station-pause`, a paused station addition, Capture extract/commit using a test tenant, PDF export, and phone/plate localization. Avoid testing send/commit routes on real customers.
- Compare `summary.bookingsAfterWhatsApp`, `summary.deliveredContacts`, and `summary.trackedBookingRate` in `/api/analytics?period=all` against independent source queries. Week/month rate numerator is `summary.bookingsFromPeriodSends`; denominator is distinct contacts with `delivered` or `read` messages whose `sent_at` falls within the same Helsinki period. Reminders must not multiply contacts. If the denominator is zero, the rate is null.
- Check the company's latest deployment SHA, branch, READY state, domain alias, required env keys, and preview/production isolation. Smoke test the domain after release; a Vercel `READY` state alone is not an authenticated workflow pass.

## Path to a truly plug-and-play product

This branch is the **initial reusable template**, not a completed white-label SaaS. To achieve the desired "change logo, connect sources, add stations" onboarding with almost no source edits, next extract a validated company manifest (brand, locale, pricing, campaign copy, features) consumed by both client and API; move the current TJ-prefixed table/raw-data contract behind tested adapters; ship a complete versioned base schema and private Storage setup; implement sender job/status and safety verification; standardize customer identity, booking provenance and timezone; add auth roles, RLS/tenant isolation *or* keep one project per company; add synthetic connector fixtures and e2e tests. These are substantial engineering/data-integration tasks, not switches already implemented by this first branch. Until then, a new company needs an agent to perform the mappings and audit described above.
